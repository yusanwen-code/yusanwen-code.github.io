## 把三个 AI 道人拉进一个群

炼丹炉（[Alchemy Furnace](https://github.com/yusanwen-code/alchemy-furnace)，开源项目）是我的 AI Agent「语言模式工程」实验场：**金丹**是封装人格特质的结构化技能包，**道人**是服用金丹的 AI Agent。之前道人之间是严格的 1v1 对话——你和一个道人聊，仅此而已。

最近完成的大功能是**群聊工作流**：把多个道人拉进同一个群，它们按各自的性格和兴趣**自主决定说还是不说**——感兴趣的接话、不感兴趣就潜水，聊到兴起还能互相辩论。这不是玩具：发言触发、@提及、轮次收束、顺序流式发言，每一环都是设计决策。

这个功能横跨三个端：Next.js 前端（群聊 UI）、Go 网关（群聊编排器）、Python 引擎（流式补全）。这篇聊聊多 Agent 是怎么被协调起来的。

## 三端分工：编排放在 Go，引擎零改动

```
前端 ChatView
  └─ POST /api/v1/chat/sse/:uuid ──► Go 网关（按会话类型分流）
                                       ├─ single → 原 1v1 SSE 逻辑（不动）
                                       └─ group  → GroupOrchestrator（新）
                                                     ├─ 轮次循环 × 成员队列
                                                     ├─ 逐道人调 Python 流式补全
                                                     ├─ 沉默检测 / @解析 / 必答队列
                                                     └─ 消息落库 + SSE 事件转发
```

| 端 | 技术栈 | 负责什么 |
|---|---|---|
| 前端 | Next.js | 群聊视图、每个道人独立头像与流式气泡、@ 候选列表 |
| Go 网关 | Gin + GORM | **GroupOrchestrator 群聊编排器**、会话/成员/消息模型、SSE 分流 |
| Python 引擎 | FastAPI | 流式补全，**零改动** |

两个关键决策：

**编排状态全在服务端。** 轮次循环、必答队列、沉默检测都在 Go 的 `GroupOrchestrator` 里跑，客户端没有任何编排职责——刷新页面后拉历史消息就能恢复视图。

**Python 引擎零改动。** 这不是巧合，是契约设计的结果：Go 把上下文拼好——`system` = 道人的语言模式 + 群规则补丁，`messages` = 带发言人标签的最近 20 条——然后调 Python 现有的流式端点。引擎只负责"生成"，不负责"群"。

## 多 Agent 协调的六个设计决策

**1. 非全员必答：主动性是数值 + LLM 判断的混合。**

每个道人有 `Proactivity` 数值（0-100，编辑页滑杆可调）。发言与否 = 这个数值注入提示词 + LLM 对话题的兴趣判断。

不做纯代码概率（拿随机数决定说不说，太死板），也不做纯 LLM 推断（完全交给模型，不可控）。数值给个性定基调，LLM 给场景做裁决——这是"混血"决策最舒服的分寸。

**2. 三向 @：被 @ 的必须回应。**

用户可以 @ 道人，道人也@道人和用户。被 @ 的道人下一轮**必回应**；被 @ 的用户只是高亮提示，不强求操作。@ 解析在服务端完成，`mentions` 落库成 JSON，下一条消息的 LLM 上下文里会带上"谁被 @ 了"。

**3. 轮次收束：防失控的结构。**

每条用户消息最多触发 **3 轮**发言，每轮每人最多说一次，某一轮全员沉默就提前结束。没有这个边界，群聊会变成无限循环的嘴仗。

**4. 顺序发言，不做并发流。**

道人们**一个接一个**地说，逐字流式输出，后面的道人能看到前面人说了什么——所以才有"接话"和"辩论"。并发多流体验酷，但消息互相看不见，就没有对话感了。顺序发言是这个功能最有味道的决定。

**5. 微信群模型：群就是持久的多人会话。**

群和 1v1 会话在侧栏混排；群名不由用户创建时填写，而是第一个问答自动生成标题，之后永不自动变更，可手动改名。成员管理支持批量邀请和踢人，人数无上限（创建时 ≥2），踢到 0 人允许——整轮沉默而已。

**6. 每轮发言都有归属。**

消息表加了 `agent_id`（NULL = 用户消息），每个道人的发言有自己的头像、姓名和气泡。成员变动（邀请/踢出）会插入 system 通知消息，但组装 LLM 历史时会过滤掉这些系统条目——**通知给用户看，不给模型看**。

## 一次群聊请求的完整工作流

```
用户发消息
  → 落库 + 解析 @
  → 轮次循环 (最多 3 轮):
      队列 = 被@的道人（必答，按被@顺序）+ 其余成员（按入群顺序），去重
      for 队列里的每个道人:
        Go 拼上下文 → 调 Python 流式补全 → 逐 chunk 转发 SSE
        → 发言落库（带 agent_id 归属）
        → 沉默检测（没说话就跳过）
      某一轮全员沉默 → 提前结束
  → done 事件，前端渲染完整群聊
```

## 复盘：多 Agent 协调教给我的

- **"不做纯代码概率，不做纯 LLM 推断"是个好框架。** 确定性逻辑和模型判断之间有个谱，多数协调问题的最优解在中间——用可控的数值定基调，用模型补灵活性。
- **顺序发言 > 并发流。** 协调多 Agent 时，让后面的 Agent 看到前面的输出，比并行快更重要。对话感来自上下文连续，不来自同时说话。
- **编排放服务端，客户端才能无状态。** 刷新不丢状态、多端可恢复，是"编排者位置"决定的，不是功能多少决定的。
- **零改动不是运气，是契约。** Go 把 `system`/`messages` 拼好，Python 只做补全——引擎不感知"群"的存在。分层清晰，才能各自演进。

项目已开源（MIT 许可），群聊编排器的完整实现和设计文档都在 [GitHub](https://github.com/yusanwen-code/alchemy-furnace) 上——`GroupOrchestrator` 值得拆开看看，一个 Go 文件怎么把一个群聊的状态机跑起来的。
